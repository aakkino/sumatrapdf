# Research: translation integration

- Query: How can SumatraPDF translate selected text and show the result in an in-app floating surface?
- Scope: mixed
- Date: 2026-09-03

## Findings

### Current implementation already covers most of the requested flow

- `SelectionToolbar.cpp:80-90` makes `CmdTranslateSelection` a default icon button in the delayed floating selection toolbar. `ShowSelectionToolbar()` debounces display by 500 ms (`Canvas.h:43-45`; `SelectionToolbar.cpp:711-733`) and positions it over or under the selection (`SelectionToolbar.cpp:516-550`). The button can be removed or reordered through `SelectionToolbarLayout` (`SelectionToolbar.cpp:104-154`).
- `SumatraPDF.cpp:12439-12464` routes that command to `ShowSelectionTranslateDialog()`. The existing dialog obtains the current text selection and enforces `Perm::CopySelection` (`SelectionTranslate.cpp:1346-1370`).
- The dialog has editable source text, source/destination language controls, engine selection, a Translate button, and a read-only result edit (`SelectionTranslate.cpp:1230-1338`). For AI engines it changes state to `Translating...`, then renders either a result or an error in the same window (`SelectionTranslate.cpp:1043-1132`).
- It is a modal owned top-level dialog: it disables the main frame before creation and re-enables it on teardown (`SelectionTranslate.cpp:1346-1388`, `SelectionTranslate.cpp:1164-1174`). It is therefore not the non-modal selection-anchored result popup described by the request.
- Google and DeepL currently use their public web translators: text and language parameters are URL-encoded and passed to the default browser (`SelectionTranslate.cpp:816-843`, `SelectionTranslate.cpp:1062`). For AI CLIs, the app launches the configured executable, reads stdout on a worker thread, parses output, and posts the completion to the UI thread (`SelectionTranslate.cpp:850-1152`).
- Existing coverage exercises the toolbar command presence and click plumbing (`tests/issue-6048.ts:32-60`) and invokes the Translate command with a selection (`tests/issue-5934.ts:107-113`). No test found that validates a successful translation response or the result UI.

### Reusable internal mechanisms

- `base/Http.h:20-27` provides `HttpPostUrl()`, a synchronous POST helper; its implementation deliberately uses WinHTTP rather than WinINet so requests do not inherit the Internet Explorer cookie jar (`base/Http_win.cpp:365-460`). It reports the HTTP status and body and caps retained responses at 1 MiB. The caller must use it off the UI thread.
- `RunAsync()` plus `uitask::Post()` is the established blocking-work/UI-completion boundary (`SelectionTranslate.cpp:1099-1152`; `base/UITask.h:9-14`). Existing completion code safely keys the result to an HWND and revalidates the dialog before dereferencing its global object, preventing a close-during-request use-after-free (`SelectionTranslate.cpp:1115-1152`).
- `base/JsonParser.{h,cpp}` is a streaming JSON parser with path callbacks and `json::EscapeStrTemp()` for placing selected UTF-8 text safely into a JSON string (`JsonParser.cpp:~530 onward`). `AIChatJsonStrTemp()` is a shallow helper for known single-string fields only (`AIChatCommon.cpp:88-125`); a provider response should use the generic parser if it needs nested arrays or robust schema handling.
- Advanced settings are generated from `cmd/gen-settings.ts`; current translation preferences are intentionally internal strings and save through `ScheduleSaveSettings()` (`cmd/gen-settings.ts:1607-1624`; `SelectionTranslate.cpp:319-332`). A persistent endpoint or credential would need the same generator path, but a plaintext settings file is not an appropriate secret store.
- `SumatraLaunchBrowser()` and `LaunchBrowserWithSelection()` are the established external-browser boundary (`SumatraPDF.cpp:439`, `SumatraPDF.cpp:9733-9772`). The latter expands `${selection}` with the shared URL encoder. Custom `SelectionHandlers` can also create command buttons, including buttons on the selection toolbar (`AppSettings.cpp:235-280`; `SelectionToolbar.cpp:158-184`).

### Recommended MVP boundary, pending product decision

Keep the current Translate toolbar command. If the product goal is an in-app result popup, add a translation-service abstraction with a single deliberately selected provider implementation, invoked only after a click, and a non-modal, selection-anchored result popup. The abstraction should own request serialization, maximum input length, cancellation/lifetime generation, response parsing, and a sanitized error enum; the popup should own only loading/result/error presentation and close/reposition behavior.

The least risky first product is either:

1. extend the existing AI-CLI path to render into a non-modal popup, retaining its existing authentication model; or
2. add a single API provider only after deciding credential storage and an explicit first-use disclosure that selected text is sent to that provider.

Do not begin with a free-form endpoint/template/key setting: it widens security and support scope before the product has a stable request/response contract. Do not send a request automatically when selection settles: an explicit Translate click is the natural consent boundary and matches the current behavior.

## Caveats / Not Found

- The requested toolbar button already exists in this worktree. The actual delta is presentation and provider behavior: a modal dialog for AI result versus browser handoff for Google/DeepL.
- No OS-backed credential storage wrapper was found under `src/`; storing API keys in `SumatraPDF-settings.txt` should be treated as an unresolved security design requirement, not an implementation shortcut.
- `HttpPostUrl()` has no exposed cancellation handle, configurable timeout, response header access, or redirect policy. A production API provider may need a narrowly extended HTTP abstraction rather than UI code calling WinHTTP directly.
- No reusable generic popup-result component was found. `SelectionToolbar` supplies a useful model for an owned, no-activate, selection-following `VirtHost`, but its current state is only a button row.
