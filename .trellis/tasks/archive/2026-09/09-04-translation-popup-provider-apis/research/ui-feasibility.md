- Query: Can the requested selection-translation popup restyle and a pure provider-configuration window be implemented with the current SumatraPDF Win32 UI stack? Which visual ideas from the previous prototype are usable?
- Scope: internal, including `D:\desktop_directory\selection-translation-popup`
- Date: 2026-09-04

## Confirmed Current State

This is not greenfield. The current worktree already has an anchored `SelectionTranslatePopupWnd`: it uses `WS_POPUP | WS_BORDER`, is owner-associated, retains initial document focus, clamps to the monitor work area, handles loading/result/error states, exposes Copy/Configure/Close controls, and repositions as the document moves (`src/SelectionTranslate.cpp:1626-1659`, `src/SelectionTranslate.cpp:1661-1704`, `src/SelectionTranslate.cpp:1782-1874`). Its provider menu is a checked native `TrackPopupMenu` (`src/SelectionTranslate.cpp:1706-1753`).

The existing full dialog is an owner-disabled, resizable `WindowBase` window with a `VBox` and native `Edit`/`DropDown` children; it is currently an edit-source/translate/result dialog rather than configuration-only (`src/SelectionTranslate.cpp:1184-1352`, `src/SelectionTranslate.cpp:1355-1400`). Converting its purpose is feasible, but is an intentional user-visible removal of its manual translation workflow.

The prior prototype confirms the intended visual vocabulary: compact header, provider selector, target language, result/status body, and compact footer. Its large rounded Fluent card, blurred/translucent surface, CSS transitions, spinner overlay, iconography, and browser layout are not evidence of an existing native implementation. The baseline native capture is materially plainer: bordered Win32 popup, readable header, native multiline edit, and native buttons.

## Recommended Native Direction

Use the existing non-modal popup for the quick result and preserve its information density: provider menu and target language in the header; one clear status/result region; Copy, Retry when applicable, Configure, and Close in the footer. Keep it square-to-small-radius with an opaque theme surface and normal Win32 text controls. This directly preserves focus, keyboard, DPI, dark-mode, RTL, placement, stale-request, and screenshot behavior.

For the pure configuration dialog, use a normal resizable captioned `WindowBase` dialog. Use a three-row `VirtListBox` on the left and a `VBox` form on the right. Fields should swap by provider: OpenAI-compatible base/model/key; Google project/key or credential method as selected by the API design; Microsoft endpoint/region/key. Use native password `Edit` for keys. A simple Test button and textual success/error status are viable; no animated or translucent status panel is needed.

## Test Implications

- Retarget `tests/selection-translate-popup.ts`: it already proves focus preservation, placement following the frame, state visibility, result controls, selection invalidation, engine change, and stale completion (`tests/selection-translate-popup.ts:150-246`). Replace AI-CLI assumptions with selected API provider behavior and add deterministic retry/error cases.
- Add configuration-window control tests for provider switch, masked key field, validation, Save/Cancel persistence, and test-status transitions. Use the existing `-dbg-control` seam rather than live keys/network.
- Screenshot capture is available through `captureWindowToPng` and is used by existing focused/ad-hoc UI tests (`tests/ad-hoc-4600-dialog.ts:14-197`, `tests/annot-filter-toolbar.ts:193-218`). Capture the popup/configuration dialog at 100% and a high-DPI setting for manual or targeted visual review; avoid brittle pixel baselines across Windows theme versions.
- Test native menu keyboard operation manually or through a focused Win32 message test. The existing popup test does not automate the actual `TrackPopupMenu`.

## Caveats / Not Found

- The requested pure configuration UI does not yet exist. The current full dialog deliberately provides manual source editing and translation; changing it is feasible but requires updated command behavior and regression tests.
- No existing generic animation, acrylic, card-shadow, or virtual-control UIA framework was found. These are not blockers for a native, polished utility UI; they are blockers for literal HTML/CSS parity.
- Existing tests establish state and geometry, not screenshot styling, native menu traversal, high-contrast, screen-reader behavior, or multiple-monitor DPI migration. Those checks remain required before a highly customized visual implementation is accepted.
